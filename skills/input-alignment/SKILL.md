# Input Alignment — 执行前认知对齐

## 一句话纲领

> **模型的上下文比用户短，主动溯源提问优先于自己内部权衡。**
>
> 在执行前用 AskUserQuestion 把不确定点抛回，比执行后做 deep-verification 长报告更省用户时间。

---

## 触发场景（任意一条命中就触发）

### 场景 1：内心打转检测

当你即将在内心说出以下任何一种话时，**立刻停下来**：

- "虽然 X 但用户明确说了 Y，那就按 Y 来"
- "用户说了 Y，可能他是这个意思也可能是那个意思，我猜是……"
- "他没提 X，我默认按 X 处理"
- "这里有歧义但用户大概率指的是 X"

这些都是**认知漂移现场**——你正在用自己的猜测填补用户上下文。不要填补，**用 AskUserQuestion 抛回去**。

### 场景 2：可质疑假设核查（输入阶段轻量核查）

用户陈述里出现承重的假设/数据/技术选择/事实主张时，套用 deep-verification 的核心 checklist（**只跑 3 条，不写报告**）：

1. **溯源**（动作 A）：这个数据/事实，用户是从哪里得到的？是一手观察、二手转述、还是猜测？
2. **循环证据**（动作 B）：用户用来支持这个判断的依据，是不是恰好被这个判断本身污染过？
3. **普通样例证伪**（动作 D）：把用户的判定规则代入一个最常见的普通样例，会不会误判？

跑完后，**不写报告**——把发现的疑点直接转成 AskUserQuestion 的选项，让用户在执行前对齐。

### 场景 3：用户主动请求 third-eye

用户说"你觉得我这么想对吗 / 帮我看看哪里没想清楚 / 我可能漏了什么"等。

→ 跑场景 2 的轻量核查，**用 AskUserQuestion 抛出 2-3 个核心分歧点**。如果发现的问题特别多（>4 个），降级到 deep-verification 走完整报告。

### 场景 4：输入有明显歧义/缺参数

- 关键技术参数未指定（如"用缓存"但没说 Redis/Memcached/本地缓存）
- 范围不清（如"处理这些文件"但没指明哪些）
- 时间/优先级模糊（如"尽快"但没说截止时间）

→ AskUserQuestion 抛选项，**不要默认值**。

---

## 反触发：什么时候**不要**问

触发要激进，但**问要克制**。出现以下信号时停止追问：

- 用户表现出"我也不确定"、"你帮我决定"、"看着办"——继续问只会加重认知负担
- 用户已经在前面几轮对话里明确给过这个信息（先回顾上下文，不要让用户重复）
- 问题本身在执行过程中自然会暴露答案（先做一步看看，比预先问 5 个问题强）

**用户表现出不确定时的处理协议：**

1. **停止追问**
2. 给 2-3 个"可能可以想清楚的方向"作为选项，让用户先选方向，而不是直接答终极问题
3. 或者把大问题 **break down 成更好回答的子问题**，按子问题逐个对齐

例：用户说"我想做个 AI 应用但不知道做啥"——不要问"你想做什么类型？什么功能？什么用户？"，而是问"你最近遇到什么重复性事情想自动化吗？/ 你身边有人抱怨什么？/ 你最想节省哪段时间？"——这些子问题比"做什么"更好回答。

## 工作流

```
用户输入
   ↓
触发检测（4 个场景任一命中？）
   ↓ 是
轻量核查（场景 2 的 3 条 checklist，仅在适用时）
   ↓
有疑点 / 不确定点？
   ↓ 是
用户是否表现出"也不清楚"？
   ↓ 否                          ↓ 是
AskUserQuestion 抛回           给方向选项 / break down 成子问题
（每次最多 2-3 个问题）
   ↓
对齐完成后执行
```

---

## AskUserQuestion 用法约束

- **每次最多 2-3 个问题**——一次性抛 4+ 个问题等于让用户写小作文
- 每个问题给 2-4 个**具体选项**+ 一句话说明，不要开放式提问
- 选项要 mutually exclusive、清晰互斥
- 第一个选项如果是推荐项，标 `(推荐)` 并说明推荐理由
- 长开放性问题（需要用户描述场景、贴文本等）直接在对话里问，**不要**用 AskUserQuestion

---

## 和相邻 skill 的边界

| Skill | 时机 | 输出 |
|---|---|---|
| `brainstorming` | 创造性新需求探索 | 来回发散讨论 |
| `input-alignment`（本 skill） | **执行前对齐**模糊/有疑点的输入 | AskUserQuestion 抛回，对齐后执行 |
| `deep-verification` | **执行后**或独立核查任务 | 完整核查报告 / inline 提问 |

本 skill 不替代 deep-verification 的承重主张核查纪律——只是把它的前 3 个动作以**轻量、对话式**的形态用在执行前。

---

## 反模式（不要这样做）

❌ "用户说了用 Redis，我也觉得有点问题但既然他说了就这么办"——这是认知漂移，触发本 skill
❌ 一次性抛 6 个 AskUserQuestion 把用户淹没——超过 3 个就拆轮次
❌ 用户说"我也不知道"后继续追问"那你大概想要什么效果？"——停止追问，给方向选项
❌ 把本 skill 用在显然不需要对齐的简单任务上（如"改个 typo"、"列一下目录"）——触发要激进但场景判断要诚实
