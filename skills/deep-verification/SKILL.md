# Deep Verification — 对抗性核查纪律

核查类任务最常见的失败不是"不够努力"，而是**在主张被陈述的那一层就接受了它**。一份 plan 说"`parent` 字段永远等于 root"，浅层核查会去读盘上的数据、看到 parent 确实等于 root、然后点头——却没意识到那个值是被采集脚本写进去的，盘上数据根本无法回答"API 到底返回什么"。

本 skill 的全部内容就是一句话拆成 6 个动作：

> **不要在主张被陈述的那一层接受它。把它追到证据真正所在的地方，再检查那个证据能不能回答这个问题。**

下面 6 个动作是一份 checklist。不是每个任务都要全跑，但每接受一个**关键主张**（load-bearing claim——错了会让结论垮掉的那种）之前，至少在心里过一遍。

---

## 核查前先做一件事：列出 load-bearing claims

在动手核查前，先把待核查对象里**真正承重的主张**挑出来——通常 2-5 条，不是全部句子。判断标准：**如果这条是错的，整个结论/方案会不会垮？** 会垮的才值得用下面 6 个动作深挖；不承重的扫一眼即可。把核查精力集中在承重点上，是深度的前提。

---

## 动作 A — 溯源到产生点

**做什么**：任何数据、数字、字段值、引用，先问"这个值是被谁、在哪一步产生的"，找到它的**生产现场**再决定信不信。

**为什么**：你看到的值往往经过了若干层加工（脚本合成、缓存、二手转述、默认值填充）。在消费端看到的样子，可能和源头完全不是一回事。不溯源，就分不清"系统本来如此"和"中间某一步把它改成了这样"。

**怎么应用**：
- 数据字段 → 找写入它的那行代码 / 那个采集步骤，而不是只看落库结果
- 数字/统计 → 找它的计算口径和输入集
- "文档说……" → 找文档里那句话本身，确认不是转述失真

**例**：plan 说"所有子回复 parent=root，所以是星型拓扑"。溯源动作 = 去读采集脚本的调用点，发现 `extract_comment(reply, parent_rpid=root_rpid)`——parent 是被函数参数硬塞的 root，API 真实的 `reply["parent"]` 从没被读过。星型至少有一部分是脚本造的，不是平台行为。**只看落库 JSON 永远发现不了这点。**

---

## 动作 B — 查证据是否循环

**做什么**：检查"用来证明 X 的证据"，是不是恰好被 X 本身（或制造 X 的那个机制）污染过。

**为什么**：循环证据是浅层核查最隐蔽的陷阱——它"验证通过"了，但其实什么都没验证。用被污染的产物去证明污染它的过程，永远自洽，也永远错。

**怎么应用**：对每一条"我查过了，确实如此"的证据反问一句：
- 这条证据，和我要检验的那个机制，是**独立**的吗？
- 如果那个机制是错的/有 bug，这条证据会不会**照样**显示"通过"？如果会，它就没有区分力。

**例**：另一份分析用"读盘上 JSON，parent 都等于 root"来证明"API 就是返回 parent=root"。但盘上 parent=root 正是动作 A 里那个覆盖 bug 造成的——证据被它要证明的东西污染了。要打破循环，必须找一条**独立**证据：直接调原始 API，看未经脚本加工的 `parent`。

---

## 动作 C — 对权威源核查

**做什么**：关于外部系统（API、库、协议、标准、第三方行为）的事实主张，去查**上游/权威文档**，而不是项目里对它的二手转述。

**为什么**：项目自带的 schema 注释、注解、"据说"往往是某个人某时的理解快照，会过时、会抄错、会想当然。外部事实要对外部权威核对。

**怎么应用**：
- 看到"这个 API 字段的含义是……" → 找官方/社区权威文档原文，对一遍
- 注意区分"我们项目的文档怎么说"和"上游系统实际怎么定义"——前者不能替代后者
- 权威源之间若打架，记下分歧，别擅自挑一个当定论（接动作 F）

**例**：plan 自带 schema 注释说 `dialog` 是"THE nesting signal（子→子信号）"。查权威社区文档 bilibili-API-collect 发现真实语义不同：`parent` 才是逐条嵌套信号，`dialog` 是整条会话链的分组 ID，二级回复的 dialog 等于自身 rpid。项目转述和上游定义冲突——以上游为准。

---

## 动作 D — 拿普通样例证伪规则

**做什么**：任何被提出的判定规则 / 阈值 / 启发式，先手算一个**最常见的普通样例**（再加一两个边界样例），看它会不会误判。

**为什么**：规则在脑子里念起来都通顺，但一代入具体值就可能崩。证伪一条规则最快的方法不是想它对不对，而是喂它一个 case 看输出。

**怎么应用**：
- 拿到 `if X then 判定为 Y` → 找一个典型的、本不该是 Y 的输入，代进去，看会不会被误判成 Y
- 特别警惕"看起来能区分"的条件——它在常见情况下可能恒真或恒假

**例**：plan 的验证规则是 `dialog != root && dialog != 0 → 这是定向子→子回复`。代入一条**最普通的二级回复**：它的 `dialog = 自身 rpid`，天然 ≠ root 且 ≠ 0——于是每一条普通回复都会被误判成"定向子→子"。规则在常见 case 上就崩了，是个假阳性机器。

---

## 动作 E — 分层：修复改了哪个维度，没改哪个

**做什么**：当有人提出"做了 X 就能解决问题"，把问题拆成多个维度，明确 X **实际改动**的是哪个维度、**原封不动**的是哪个维度。别让一个维度的修复，偷偷夹带另一个维度的结论。

**为什么**：一个技术修复常常只动了某一层（比如拓扑结构），却被顺势当成把另一层（比如语义解释）也解决了。两层混在一起，结论就会越界。

**怎么应用**：
- "修了 X，所以 Y 也成立了" → 拆开问：X 改的是哪一层？Y 属于哪一层？是同一层吗？
- 给出"X 修复了 ___，但**没有**修复 ___"的明确边界

**例**：恢复 `parent`/`dialog` 字段，修的是**拓扑层**（星型变星+链，betweenness、社区检测变得可解释）。但它**没有**修**语义层**——回复边的方向仍是"响应/聚合"，和转发边的"扩散/放大"相反。所以"拓扑修好了"不能推出"HITS Authority 就能解读成信息放大器了"。一句话：修拓扑 ≠ 守语义，两件事必须分开 claim。

---

## 动作 F — 标注未验证项 + 指定最便宜的裁决实验

**做什么**：诚实区分"我已经核实的"和"我尚未核实但结论依赖它的"。对每个承重的未验证项，指出**能一锤定音的、成本最低的那个实验**。

**为什么**：核查的价值不只在于给出判断，更在于**精确定位不确定性**。把"还没证实但很关键"的点摊开，并告诉对方"做这一个动作就能定下来"，比假装全部都已确定有用得多，也更诚实。

**怎么应用**：
- 结论里每条承重主张，标记 ✅ 已核实 / ❓ 依赖但未核实
- 对每个 ❓，写出最小裁决实验：调一次 API、跑一个查询、读一个文件——哪个最便宜且能直接回答
- 如果你和别人（或别的分析）结论相反，明确指出"分歧点是什么 + 哪个实验能裁决"

**例**："我依据脚本调用点 + 权威文档判断 API 真实 parent 在三级回复会指向直接上级，但我没跑真实 API。另一份分析结论相反。裁决实验 = 用原始 API 拉一页子回复，打印每条的 `root`/`parent`/`dialog` 三字段，15 分钟见分晓。在那之前，方案里两个字段都先存下来，零成本对冲两种可能。"

---

## 输出格式：怎么把核查结果交付

核查类任务的产出，建议长这样（按需裁剪）：

```text
## 承重主张清单
（列出 2-5 条会影响结论成败的主张）

## 逐条核查
| 主张 | 结论 | 用了哪个动作 | 证据 / 反例 |
|---|---|---|---|
| ... | ✅成立 / ❌不成立 / ❓未决 | A溯源 / B循环 / C权威 / D证伪 / E分层 / F未验证 | ... |

## 关键分歧（如果有）
- 分歧点：...
- 裁决实验：...（最便宜的那个）

## 净结论
（哪些可信、哪些要改、哪些必须先实验才能定）
```

报告时**带上证据位置**（文件:行号、文档链接、API 字段），让对方能自己复核——核查的可信度本身也要经得起核查。

---

## 多份分析对比时

如果任务是"几份分析哪份更靠谱"，对每份跑一遍 6 动作，重点看：
- 谁**溯源**了、谁只看了二手结论（动作 A）
- 谁踩了**循环证据**（动作 B）——这往往是分水岭
- 谁的规则经得起**普通样例**（动作 D）
- 谁**诚实标注**了未验证项、谁假装全确定（动作 F）

然后明确指出：每份**独有的有效贡献**是什么（哪怕整体较弱的分析，也可能有一两个别人没想到的点，值得吸收），以及它们之间**有没有事实性冲突**需要实验裁决。好的对比不是排名，是把每份的增量拆出来、把冲突点摊明。

---

## 什么时候不要过度套用

这是核查纪律，不是仪式。**简单、单步、低风险**的任务别硬套——给一个明显 typo 改个字、回答一个事实性小问题、跑一条确定的命令，不需要列承重主张、不需要裁决实验。过度套用会把轻量任务拖成噪音。

判断线：**这个主张错了，代价大不大？** 代价大（影响方案走向、写进论文、指导后续大量工作）→ 值得深核查；代价小、可秒回滚 → 直接做。把深度留给真正承重的地方。
